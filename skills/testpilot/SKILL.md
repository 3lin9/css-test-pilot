# csspilot

## What is csspilot

csspilot is an AI Native cross-platform testing infrastructure.

It lets AI understand, generate, validate and run business tests for Web and Mini Program apps.

csspilot is a **tool, not a business test project**. After a test-point checklist exists, business cases are native scripts in the business project. Web uses Playwright, mini programs use miniprogram-automator, and APIs use node:test. csspilot does not translate a shared YAML case into those frameworks.

## When to use

Use csspilot when the user wants to:

- review test requirements for testability
- create business test cases
- validate test cases
- run tests
- inspect test results

## Core workflow

1. Understand user requirement
2. Review requirements, expand the rule matrix, and map QA coverage (`workflows/test-requirements-review.md`)
3. Inspect project
4. Identify test target
5. Observe the live page with that platform's MCP, then write one native script per test point (`workflows/create-case.md`, `rules/native.md`). Web uses Playwright MCP. Mini Program uses wechatide MCP.
6. Run that script with `npx csspilot run <file>`. The run executes the script. It does not replay the MCP session.
7. Analyze the framework result (`workflows/analyze-result.md`)

## Important rules

- Write the test in the current platform's framework. Do not write a YAML case for a new test point.
- Web scripts import `test` / `expect` from `tests/e2e/web/fixtures.ts` (generated by `csspilot init`), which wraps `@playwright/test` and auto-collects console + network for the report. Mini Program scripts call miniprogram-automator directly. API scripts call fetch directly.
- When writing a Web or Mini Program script, observe the live page with Playwright MCP or wechatide MCP first, then save the confirmed steps as the native script. `csspilot run` executes that script.
- Business scripts belong to the business project.
- Prefer existing project conventions.
- Never invent locators, selectors, or routes without evidence from the project.
- A test point that spans platforms becomes separate scripts, one per platform.

## CLI

```bash
npx csspilot init      # install csspilot into the current project
npx csspilot run       # run native scripts under tests/e2e/{web,miniapp,api}
npx csspilot run tests/e2e/web/order-create.spec.ts
npx csspilot report    # generate JSON + HTML report
npx csspilot report --trace  # replay the latest failed case in Playwright trace viewer
npx csspilot doctor    # health check (config / cases / adapters / env / server)
npx csspilot ci init   # generate csspilot CI workflow template
npx csspilot sync-metadata  # sync case metadata to csspilot Server (CI, after git push)
```

Native `run` normalizes each framework's structured output into `result.json` and applies the tri-state exit code contract: `0` passed/skipped, `1` failed (product bug) or inconclusive (prerequisite missing), `2` blocked (environment/prerequisite, not a product regression). Scripts mark the latter two by throwing errors prefixed `[TESTPILOT:ENVIRONMENT_UNAVAILABLE]` / `[TESTPILOT:PREREQ_VARIABLE_MISSING]`.

## Directory map (business project)

- `.agents/skills/testpilot/` — this skill (AI usage spec)
- `.testpilot/` — csspilot runtime state and artifacts
- `tests/e2e/web/` — Playwright specs; `fixtures.ts` is the shared import point (console/network observation)
- `tests/e2e/miniapp/` — miniprogram-automator scripts
- `tests/e2e/api/` — HTTP scripts
- `tests/e2e/data/` — JSON/YAML inputs read by those scripts
- `tests/e2e/reviews/` — requirement matrix and QA coverage artifacts
- `testpilot.yaml` — project-level csspilot config
